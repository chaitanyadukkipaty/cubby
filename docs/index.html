A home for the apps your agents build.

Cubby is a server you host once and share with friends or colleagues. Everyone asks their AI coding agent for an app, and Cubby gives it a real database, user accounts and a live URL. Everyone can open everyone's apps; only you can change yours.

Why

Why Cubby exists

Coding agents can now write a complete web app from one sentence. Hosting it is the hard part: the app needs a database, logins, somewhere to live, and a URL your friends can open. Hosted builders like Lovable solve that, but your apps and data live on someone else's platform, and you can't use the agent you already like.

Cubby is the self-hosted version for a group of people who trust each other: a family, a team, a group of friends. One person runs a small server. Everyone else uses whichever agent they already have.

Architecture

How it works

Everything runs in one Docker container: Caddy in front for HTTPS, the Cubby server, and a shared PocketBase database. Each app gets its own subdomain and its own walled-off slice of the database.

One subdomain per app

Each app is its own website, so apps can never read each other's logins in the browser.

One database, walled off

App polls owns collections named polls__*. The proxy refuses anything else.

Static frontends, scheduled jobs

Apps are Vite + React + Tailwind builds; security lives in database rules. Code that runs on a schedule goes in sandboxed jobs.

Admin · 5 minutes

Install a server

You need a Linux VPS (Ubuntu or Debian work best) with ports 80 and 443 open (an IP-only install can use another port). 1 vCPU and 1 GB of RAM is enough for a group of friends. Run:

curl -fsSL https://raw.githubusercontent.com/chaitanyadukkipaty/cubby/main/install.sh | sudo bash

The installer asks four questions, then installs Docker if needed, builds the image and starts Cubby:

QuestionWhat to answer
Domaine.g. cubby.example.com, or leave blank to use the server's IP address
Admin emailYour email. You'll log in to the dashboard with it.
Admin passwordAt least 8 characters. It isn't stored on disk after setup.
Name your cubbyWhat everyone sees, e.g. Priya's Cubby. Press Enter to use the suggested name; you can rename it later.

When it finishes it prints your URL and a signup code like otter-maple-42. Those two things are all your friends need.

Domain or IP?

ModeApp URLsHTTPS
Domain (recommended)https://polls.cubby.example.comAutomatic, free certificates per app
IP onlyhttp://polls.203-0-113-5.sslip.ioNo. Passwords and tokens travel unencrypted.

For a domain, add two DNS A records pointing at the server before installing: one for cubby.example.com and a wildcard for *.cubby.example.com. Started on an IP? Switch any time:

sudo cubby-server set-domain cubby.example.com

Port 80 already in use?

If another web server (nginx, Apache, another container) holds port 80, an IP-only install tells you what holds it and offers a free port instead, like 8080. Press Enter to take it. Your URL becomes http://203-0-113-5.sslip.io:8080 and apps http://polls.203-0-113-5.sslip.io:8080; open that port in your cloud provider's firewall. Pass --http-port 8080 to choose it up front.

The port is part of every URL your friends and their agents have saved, so it never changes on its own: if something else takes it later, cubby-server upgrade and rebuild stop and say what to free. A domain always needs ports 80 and 443, because Let's Encrypt only checks those; the installer and set-domain refuse until they're free.

Which version gets installed?

The latest release, unless you choose. Pass options after bash -s --:

curl -fsSL https://raw.githubusercontent.com/chaitanyadukkipaty/cubby/main/install.sh | sudo bash -s -- --version 0.1.1   # a specific release
curl -fsSL https://raw.githubusercontent.com/chaitanyadukkipaty/cubby/main/install.sh | sudo bash -s -- --ref my-branch   # any branch, tag or commit

A --ref install isn't a release, so it hasn't been through release testing; use it to try a fix early. To install without any prompts, answer the questions with --domain (or --no-domain), --admin-email, --admin-password-file and --name. --http-port and --pb-port pick the host ports when the defaults (80 and 8090) are taken.

Admin

Invite people

Send your friends the server URL and the signup code. In the dashboard's Admin tab, Copy invite copies both. They open the URL, sign up with the code, and land on their dashboard, headed with your server's name.

Rotate code invalidates the old code for new signups; existing accounts keep working.

Open signup drops the code requirement entirely. Leave it off for a server on the public internet: bots find open signup forms within days.

Signup and login are rate-limited to 10 attempts a minute per IP address.

Everyone · once

Connect your agent

Each person pastes one prompt into their coding agent. It's shown on their dashboard with the server's name and URL filled in:

I'd like you to set up Cubby: Priya's Cubby at https://cubby.example.com, a self-hosted server where you build and host web apps for me.
Install it as a skill if I have npm: npx skills add chaitanyadukkipaty/cubby --skill cubby -g
If not, do this instead: curl -fsSL https://cubby.example.com/skill.sh | sh
After installing, read ~/.agents/skills/cubby/SKILL.md and follow its Setup to connect to https://cubby.example.com (you'll send me a link to approve), review the docs at https://cubby.example.com/docs.md and ask me what I'd like to build.

The agent installs the cubby skill, instructions that teach it how to use Cubby, with npx skills add from GitHub (or the server's own /skill.sh without npm), sends you a link to approve, and adds the server to your list by name. It's a prompt, not a bare curl … | sh, so your agent knows what you're asking for instead of flagging an unknown script. Giving your agent just the server URL works too: anything that isn't a browser gets the setup steps as plain text from the root page. The skill goes in ~/.agents/skills/cubby and is linked into every agent it finds:

Claude Code

~/.claude/skills

Codex

~/.codex/skills

Cursor

~/.cursor/skills

OpenCode

~/.config/opencode/skills

The skill is short on purpose. It tells the agent to read the server's live /docs.md first, so limits and rules always match the server you're on.

Belong to more than one cubby?

Run each server's command once. They all share one skill and one cubby command, and your agent knows them by name: say “build it on Acme Cubby”, and if you have several and don't say, it asks once. Each app remembers which server it lives on, so later changes always go to the right place.

Servers can run different versions of Cubby. The cubby command handles that for you: for each server it uses a CLI that matches that server's version, downloading it once into ~/.cubby/cli/ when needed.

The first time your agent connects

The agent installs the cubby CLI from your server by itself, then sends you one message:

To connect me to your Cubby account, open this link and click Approve (you can sign up there if you're new).

You open the link, check the code matches, and click Approve. The page says which agent is asking, like “Claude Code on chaitanya-mbp wants access”. The agent carries on by itself. You never paste passwords or tokens into a chat.

Every login is its own agent

Each approved cubby login gets its own key and a name from the agent tool it runs under (Claude Code, Codex or Cursor, otherwise “Terminal”; --client sets it) and the machine it's on. Connect Claude Code on your laptop and Codex on your desktop and Cubby sees two agents, not one shared token. Agents that ran an older CLI get a dated name like “Agent · 2026-10-17”.

cubby agents
#   ID               NAME                         TOOL         MACHINE        CREATED     LAST SEEN
#   k0m2c8d1x4e5f6g  Manual token                 -            -              2026-10-01  2 days ago
# * r8a2kq0m1vx7c3d  Claude Code · chaitanya-mbp  Claude Code  chaitanya-mbp  2026-10-17  just now
#   p3n7w9s2t5u8v1y  Codex · desktop              Codex        desktop        2026-10-17  3 hours ago

The * marks the agent asking. The token on your dashboard, for scripts and CI, shows up as Manual token; tokens from before agents existed keep working and appear there too. Last seen is when the agent last used its key, updated at most once a minute.

Rename or revoke an agent

Done with an agent, or lost the laptop it ran on? Revoke it, and its key stops working on its very next request. Your other agents keep working, and any of them can do it for you: just ask.

cubby agents rename p3n7w9s2t5u8v1y "Old desktop"
cubby agents revoke p3n7w9s2t5u8v1y --yes   # refuses without --yes

An agent can revoke itself too; the CLI then forgets the dead token, like cubby logout. You can only see, rename and revoke your own agents. Regenerate on the dashboard replaces only your manual token; agents keep their own keys.

Everyone

Build an app

Just ask, in plain words. For example:

Build me an app where my friends can create polls and vote on them, and host it on Cubby.

The skill tells the agent to work like Lovable: decide the details itself, build something complete and polished, ship early, and report back in plain language. A typical run:

  1. Picks a name, then runs cubby init friend-polls to scaffold Vite, React, Tailwind and the database client.
  2. Designs the data model and its security rules in cubby/schema.json.
  3. Writes the UI, then ships with cubby deploy: schema, build and upload in one step.
  4. Tests its own rules, then tells you the URL, what it built, and ideas for next steps.

Everyone on your server can open the app and sees it in Everyone's apps. Ask for it to be unlisted if you'd rather share only the link.

Changing an app later. The server stores built output, not source code. Keep working in the folder the app was built in, and ask your agent for changes there.

Scheduled jobs

Some things should happen without anyone opening the app: closing polls when they expire, a weekly digest, a reminder before a deadline, pulling prices from an API every hour. Ask for it the same way:

Close polls automatically when they expire, and email everyone a digest of new polls every Monday.

The agent writes one file per job in the app's cubby/jobs/ folder, with a schedule in cron syntax (always UTC):

// cubby/jobs/close-expired-polls.ts
export const schedule = '*/15 * * * *';           // every 15 minutes

export default async ({ pb, env, log, fetch }) => {
  const now = new Date().toISOString().replace('T', ' ');
  const expired = await pb.collection('polls').getFullList({ filter: pb.filter('closed = false && closes_at < {:now}', { now }) });
  for (const poll of expired) await pb.collection('polls').update(poll.id, { closed: true });
  log(`closed ${expired.length} polls`);
};
  • Shipped with the app. cubby deploy bundles the jobs with the frontend, and cubby rollback brings back the jobs of that deploy.
  • Its own data, past the rules. A job's pb acts as admin, but only for that app's collections. Other apps and the server's own data are out of reach.
  • Secrets stay secret. API keys are set with cubby env set NAME=value, stored encrypted, never shown again, and given only to the app's jobs as env.NAME.
  • Checked right away. cubby jobs run <job> runs one now and prints its log, so the agent tests each job before telling you it's done. The app's card on your dashboard lists its jobs, with Run now, Pause and the last log.
  • Safe to miss. A run that's due while the previous one is still going is skipped, and runs missed while the server was down aren't caught up later.

Installing the CLI by hand needs Node.js 20 or newer:

npm i -g https://cubby.example.com/cli.tgz

The CLI always comes from your own server, so its version matches the server. It warns you if they drift apart.

Data and security rules

Each app describes its data in cubby/schema.json. Names are written without the app's prefix; Cubby adds it.

{
  "collections": [
    { "name": "users", "type": "auth",
      "fields": [{ "name": "name", "type": "text", "max": 100 }],
      "createRule": "",                                 // anyone can sign up
      "viewRule": "id = @request.auth.id" },
    { "name": "tasks", "type": "base",
      "fields": [
        { "name": "title", "type": "text", "required": true },
        { "name": "done", "type": "bool" },
        { "name": "owner", "type": "relation", "collection": "users", "maxSelect": 1 }
      ],
      "indexes": [{ "columns": ["owner"] }],
      "listRule": "owner = @request.auth.id",           // you only see your own tasks
      "createRule": "@request.auth.id != '' && @request.body.owner = @request.auth.id",
      "updateRule": "owner = @request.auth.id",
      "deleteRule": "owner = @request.auth.id" }
  ]
}

Rules are the security

A missing rule means nobody can do that action from the app. "" means anyone, even logged out.

Push never deletes

Fields you remove from the file are kept, with their data, until you run cubby schema drop.

Types don't change in place

Changing bool to text is refused. Add a new field instead.

Field types: text, editor, number, bool, email, url, date, autodate, select, file, relation, json, geoPoint. Rule syntax follows PocketBase API rules.

Admin

Running the server

The Admin tab shows users, apps, disk usage and limits. As admin you can:

  • Rename the server. The name shows on the dashboard, the sign-in page and when people connect an agent
  • Rotate the signup code or turn on open signup
  • Set apps per user and the maximum deploy size
  • Disable a user (their apps stay online) or delete them with their apps
  • Delete any app, for example to free disk space
  • See every app's scheduled jobs and how their last run went, set the time limit per run (60 seconds by default), or stop all jobs at once

Admins can't deploy into or edit other people's apps.

Updates. Once a day the server asks GitHub for the latest Cubby release. When there's a newer one, the Admin tab shows Update available with a link to the release notes and the command to run. Turn the check off in the Admin tab, or set CUBBY_UPDATE_CHECK=0 in /opt/cubby/cubby.env to disable it completely.

Versions. A server built from a release shows its version, like 0.1.1. Anything else shows the commit too, like 0.1.1-dev+b2cb75c, so you always know which code is running.

Backups run every night at 03:00: a full database backup plus all deployed sites with their jobs, and the key that decrypts app secrets. The last 7 are kept. Restoring rolls back every app on the server, so it's for real accidents.

Disk and backups from your own machine

You don't need to SSH in to see where the disk goes or to tidy up backups. Logged in as the admin, you or your agent can run:

cubby admin storage                          # database, uploads, current and older deploys, backups, free disk; per app
cubby admin backups                          # backups by date: database size, sites size, total
cubby admin backups create                   # back up now (waits until done; --no-wait returns at once)
cubby admin backups delete 2026-10-01 --yes

A backup is a pair of files for one day, cubby-<date>.zip (the database) and sites-<date>.tar.gz (sites, jobs and the secrets key). Deleting always removes both. Deleting the newest backup prints a warning, and deleting the only one is refused unless you add --leave-none. Only one backup runs at a time. Storage is measured when you ask and the result is reused for 5 minutes; nothing is stored. Restoring stays on the server on purpose: sudo cubby-server restore <date>. Anyone who isn't an admin gets a clear "needs an admin account" error.

The PocketBase admin UI is only reachable from the server itself: ssh -L 8090:127.0.0.1:8090 you@server, then open http://localhost:8090/_/. If 8090 was taken at install, the installer printed the port it used instead (CUBBY_PB_PORT in /opt/cubby/cubby.env).

Trust

Security model

Cubby is built for groups that know each other. It keeps apps apart and limits the damage of mistakes, but it is not a hostile multi-tenant cloud.

  • Apps are isolated. Each app's database calls go through a proxy that only allows that app's collections and file storage. It rejects logins issued by other apps and blocks the database admin UI and settings.
  • Only owners change apps. Deploying, changing the schema and deleting all require the owner's token. Admins can delete apps but can't edit them.
  • Agents never see passwords. They log in through a link you approve in the browser.
  • Deploys are inert files. Uploads are unpacked as plain files only (no symlinks), into folders that can't be escaped. Job code is moved out of the site, so it's never served.
  • Jobs are sandboxed. Each run is a separate Node.js process with the permission model on: it can't read the server's files, start processes or see its environment, and it can only connect to public internet addresses, never to the database or anything else on the server's network. Its database client reaches only its own app's records, checked by the same code as the proxy. Runs have a time limit and a 128 MB memory cap, and at most two run at once. This stops accidents and snooping between apps; like the rest of Cubby, it assumes people with accounts aren't attackers.
  • Secrets are encrypted with a server key that's kept outside the database (and backed up with it). The database admin UI shows only ciphertext, and values are never shown again after they're set.
  • Every agent has its own key. Each approved login gets a separate token, named after its tool and machine. Your manual token is stored so the dashboard can show it again. cubby agents revoke cuts one agent off immediately, and Regenerate replaces the manual token without touching agents.
  • Use a domain. On an IP-only server, traffic is unencrypted.
  • One outbound request of its own. The daily release check to GitHub is the only request Cubby itself makes, and it sends nothing about your server or users. Admins can turn it off. Apps' scheduled jobs make the requests their owners write.

Answers

FAQ and limits

Can apps have server-side code?

On a schedule, yes: scheduled jobs run code every few minutes, hours or days, with their own app's data and secrets. Code that runs per request (API endpoints, hooks) isn't supported; browsers talk to the database directly, under its rules. That covers most group tools: polls, trackers, lists, boards, small games.

Can people outside the server use an app?

Yes. Apps are public at their URLs, and each app has its own sign-up. Only the dashboard and gallery need a Cubby account.

How big can it get?

All apps share one SQLite database, which comfortably serves a group of friends or a small team. One very busy app slows the others. There's no per-app data quota yet; the Admin tab shows disk use so you can clean up.

Which agents work?

Any agent that supports skills (Claude Code, Codex, Cursor, OpenCode). Others can still use Cubby by reading <server>/docs.md and running the CLI.

What's not supported yet?

Server code that runs per request (API endpoints, hooks), custom domains per app, single sign-on across apps, and app emails (verification, password reset). Jobs can send email through a provider's API with your own key.

Can I use several Cubby servers?

Yes. Paste each server's setup prompt into your agent once; the first one becomes the default for new apps; your agent then picks a server by its name, and asks if it isn't sure. cubby servers lists them and cubby use sets the default. Servers on different Cubby versions work side by side: the CLI always matches the server it's talking to (in an app folder, the server in cubby.json), downloading that server's version of the CLI once. Agents find out what a server supports with cubby help --json. Servers older than Cubby 0.1.1 aren't supported; the CLI tells you to ask the admin to run sudo cubby-server upgrade.

A server moved to a new address. How do I move my app?

Each app's cubby.json remembers its server's address. Log in to the new address, then run cubby link <app> --server <new-url> in the app's folder.

Which version am I on, and how do I update?

The Admin tab shows the version at the bottom and tells you when a newer release is out. On the server, sudo cubby-server version shows the details and sudo cubby-server upgrade updates (it backs up first). Normal releases go 0.1.1 → 0.1.2; only a major change moves to 0.2.0.

My agent's login link expired.

Links last 10 minutes. Ask the agent to try again; it starts a fresh one.

Contribute

Develop Cubby

git clone https://github.com/chaitanyadukkipaty/cubby && cd cubby
cp .env.example .env
npm run setup        # downloads PocketBase into ./bin, installs deps
npm run dev          # http://localhost:8080, apps at http://<app>.localhost:8080
npm test             # unit, integration and browser tests

The repo has three parts: server/ (control API, hosting, database proxy), cli/ (the CLI, app template and agent skill) and docker/ + install.sh (packaging). The main branch is protected: every change lands through a pull request with passing tests. Before opening one, read the contribution guide: branch naming, Conventional Commits, tests at every level of the pyramid, and docs in the same PR.
